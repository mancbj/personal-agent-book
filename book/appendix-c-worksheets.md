# 附录 C · 可复用工作表

本附录把第 7—9、11—12 章的方法整理成可以复制、填写和复查的表。空栏供你记录自己的条件，不是产品已有能力的承诺。首次使用先选一项低风险任务，同一张表可以随版本更新。

分章 Markdown 与全套 ZIP 都保留本附录，可复制表格到自己的文档。不要把密码、令牌、支付卡号或不必要的个人资料写进表里；用资源名称、凭证存放位置和撤销入口代替。

## 表一：选型对照

先写任务，再各填一份候选方案。只有完成验收的结果才能放到“已验证”，公告里写有的能力放到“资料说明”。

| 项目 | 我的记录 | 怎样确认 |
| --- | --- | --- |
| 一件真事 | 任务：＿＿；完成标准：＿＿ | 用一句话描述可核验的结果 |
| 条件与日期 | 日期、地区、账号／组织：＿＿ | 记录实际试用条件 |
| 候选与版本 | 产品、客户端、套餐、模型：＿＿ | 以账号和配置中的实际值为准 |
| 资源位置 | 邮箱、目录、应用、内网或设备：＿＿ | 列出真正需要的资源 |
| 执行与推理 | 执行位置：＿＿；模型位置：＿＿ | 不只填写本地／云端标签 |
| 访问动作 | 读取：＿＿；写入：＿＿；对外动作：＿＿ | 分清连接与操作支持 |
| 数据约束 | 允许发送什么、发往哪里：＿＿ | 检查工具、模型、日志与副本 |
| 费用与维护 | 基础费用、超额规则、维护人：＿＿ | 钱与时间分开记录 |
| 证据 | 资料说明：＿＿；已验证：＿＿ | 保存来源和实际结果 |
| 决定 | 继续、缩小任务、换方案或停止：＿＿ | 写下决定所依赖的证据 |

如果候选方案无法触及必须的本地资源，不应靠扩大授权填补能力空白。考虑合适的本地执行组件，或换一种任务分工。

## 表二：一周试用记录

先完成一次可比的手工基线。下面每一行记录一次尝试，失败、超时与人工接管也保留。必要审批和可避免的催促分开计数。

| 时间与条件 | 结果与介入 | 投入与费用 |
| --- | --- | --- |
| 手工基线：任务规模＿＿ | 验收标准与结果＿＿ | 主动分钟＿＿；等待＿＿；直接费用＿＿ |
| 第一次：日期／版本＿＿ | 成功、失败或接管＿＿；审批＿＿；催促＿＿ | 配置、交代、复核、纠错分钟＿＿；费用＿＿ |
| 第二次：只改变＿＿ | 验收缺项＿＿；主要介入原因＿＿ | 主动分钟＿＿；等待＿＿；费用＿＿ |
| 第三次：条件＿＿ | 复用约束情况＿＿；异常＿＿ | 主动分钟＿＿；维护分钟＿＿；费用＿＿ |
| 暂停与恢复：方法＿＿ | 状态能否说明＿＿；有无重复动作＿＿ | 恢复投入＿＿；新增费用＿＿ |
| 一周结论：样本＿＿次 | 成功＿＿次；接管＿＿次；不必要打断＿＿ | 主动时间合计＿＿；总费用＿＿ |

净时间收益的计算口径：**同等数量、质量可比的手工主动时间 − 配置、交代、审批、监督、复核、纠错和维护的主动时间合计。** 配置只计一次；若只观察短期，不假定它可以无限摊薄。运行耗时与自己的主动投入分开，钱也不要与分钟直接相减。

不要把三次成功写成普遍成功率。写“在这些条件下，三次均达到本人的验收标准”，读者才能知道证据有多大。

## 表三：任务委托单

这张表在开始前填写，条件变化时修订。代理应复述最重要的边界；不一致时先澄清，不启动相关动作。

| 字段 | 可以直接填入的内容 |
| --- | --- |
| 目标与交付 | 我希望得到＿＿；结果保存到＿＿；验收依据是＿＿ |
| 输入与范围 | 使用＿＿资料；日期范围＿＿；排除＿＿ |
| 允许读取 | 账号／目录／对象＿＿；不需要的资料＿＿ |
| 允许执行 | 可以直接＿＿；只能准备草稿＿＿ |
| 需要确认 | 对外发送、删除、改签、付款等具体动作＿＿ |
| 预算与期限 | 费用口径＿＿；额度＿＿；截止时间和时区＿＿ |
| 等待与跟进 | 等待＿＿；触发下一步的条件＿＿；汇报频率＿＿ |
| 异常与暂停 | 登录失效、信息冲突、条件变化等停点＿＿ |
| 恢复规则 | 先核对已发生动作，再从＿＿继续；重试限度＿＿ |
| 收尾 | 留存＿＿；撤回临时权限＿＿；关闭触发器＿＿ |

**示范填写：每周资料简报。** 使用三项指定公开来源，整理本周变化，每项结论带日期和链接，输出一页 Markdown 草稿；不登录私人账号，不对外发送。没有新内容也说明。来源不可访问时标注缺项，不编造补齐；周五 17:00 前交付，时区按用户所在地确认。自动重复前，先人工验收一次。这是教学示例，不是某产品的实测成绩。

## 表四：权限与长期规则

一项长期规则对应一行。工作、生活与财务分别管理；多个角色共享环境时，必须按真实的隔离单位检查。

| 权限对象与动作 | 授权规则 | 停止与复核 |
| --- | --- | --- |
| 资源＿＿；动作＿＿ | 单次／常设＿＿；范围＿＿ | 授权人＿＿；撤销入口＿＿ |
| 对象与渠道＿＿ | 额度＿＿；次数＿＿；到期＿＿ | 哪些变化必须重新确认＿＿ |
| 文件写入／删除＿＿ | 输出目录＿＿；备份规则＿＿ | 如何确认已写入，能否恢复＿＿ |
| 对外消息／付款＿＿ | 收件人或商家＿＿；确认条件＿＿ | 已发生动作怎样补救＿＿ |
| 角色与账号＿＿ | 实际共享或隔离范围＿＿ | 谁能看到资料、凭证与日志＿＿ |

规则示例可以是“每周把草稿保存到指定测试目录”，不能只写“信任这个代理”。关闭窗口、暂停任务、撤销令牌和取消已经产生的订单，各自对应不同操作。

## 表五：暂停、恢复与迁移

先暂停旧环境中的相应任务和触发器，再核对状态。未确认之前，避免让新旧环境同时对外行动。

| 步骤 | 要带走或检查什么 | 我的结果 |
| --- | --- | --- |
| 盘点 | 已完成、待办、等待回复与进行中的外部动作 | ＿＿ |
| 导出 | 所需事实、偏好、任务状态、方法和配置 | ＿＿ |
| 保护 | 副本存放、访问权限；避免不必要凭证随包流转 | ＿＿ |
| 新环境 | 版本、模型、工具、资源与数据路径 | ＿＿ |
| 重新授权 | 凭证按服务重新配置，长期规则逐项确认 | ＿＿ |
| 恢复小任务 | 先读取／草稿，检查状态、结果与费用 | ＿＿ |
| 收尾 | 停用旧触发器、撤销旧访问、按需保留或删除资料 | ＿＿ |

恢复的成功标准不是“导入无报错”，而是新环境能在正确状态下继续一项低风险任务，旧环境没有重复执行。聊天、记忆、业务订单与登录权限，分别核对。

## 表六：异常记录与勘误提交

| 项目 | 我的记录 |
| --- | --- |
| 发生条件 | 日期、版本、套餐、地区、资源与任务＿＿ |
| 预期与实际 | 原授权＿＿；预期＿＿；实际动作／结果＿＿ |
| 已发生与未发生 | 已提交＿＿；仍在等待＿＿；已暂停＿＿ |
| 证据与处理 | 去除敏感信息的日志／截图＿＿；服务工单＿＿ |
| 复现与判断 | 能否复现＿＿；已证实部分＿＿；仍不确定＿＿ |
| 书稿勘误 | 章节与原句＿＿；建议改法＿＿；可核对来源＿＿ |

提交到本书 [Issues](https://github.com/mancbj/personal-agent-book/issues) 时，只提供足以判断问题的信息，删去密钥、订单隐私与他人的个人资料。个人体验、可复现问题和系统性结论有不同证据门槛；表格帮助保留这些区别。
