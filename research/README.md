### 部署生态的写作边界

本地派的不可替代场景按资源与约束具体展开：本机专有应用及私有文件、不公开的内网和 NAS、本地硬件、严格不外发资料的处理，以及满足完全本地依赖时的离线任务。各产品并非天然支持所有场景，需明确适配接口、模型、工具和授权的条件。

两条分类轴需要分开：一是运行位置（本地、云端、混合），二是生态与控制方式（开放运行时、自托管、平台托管、厂商整合服务）。LightVela 云端运行 Hermes 的官方说明，是这两条轴相交的具体例子。云端服务通过本地执行组件访问本机时，描述为混合部署，说明数据流与权限；不能把“本地代理”直接写成“本地模型”或“零外发”。

## 分章节写作规则

1. 按作者要求，先确认 [目录](../TOC.md)，再开始正文。
2. 每章先概说，再举例与解释；必要术语放在读者遇到问题之后介绍。
3. 重要章首使用信息图，图必须帮助读者回答具体问题，与正文共用定义和出处。
4. 事实、厂商承诺、他人体验、作者分析与未来情景分别标明，不凭文风确定可信度。
5. 涉及产品的时间敏感事实附日期、地区、版本或套餐范围；核实过程记录来源与访问日期。
6. 观点矛盾保留为问题、反例或不同适用条件；事实矛盾经核查后校正，无法解决则明确留空。
7. 不用宣传演示推导普遍成功率，不以个体帖子推导整体口碑，不用主产品数据代替新子产品表现。
8. 每章留下来源及待确认项；定稿时统一可追溯引用，清理会话内部引用和无依据的强断言。
9. 本地派与云端派对等展开；把部署位置、模型位置、生态开放性和数据流分别说明，重要图表包含混合部署的交集。
10. 曝光、官宣、内测、公开测试、邀请制及全面开放分别标注；增长统计写明指标、基数、区间及披露方，无法补齐时保留为有出处的自报线索。

## 简洁仓库与交付计划

第一、二篇已写成审阅版，来源快照见 [第一篇来源记录](part1-sources.md)与[第二篇来源记录](part2-sources.md)。仓库按实际需要使用下列结构，不提前铺设后续空章节：

```text
README.md             阅读入口、版本与贡献说明
TOC.md                全书目录
LICENSE               保留仓库现有许可证
book/                 编号排序的章节 Markdown 与附录
assets/               共用信息图、样式与必要字体资源
research/             分歧、事实核查与来源记录
scripts/              一套构建入口及其必要依赖
.github/workflows/    构建检查与 GitHub Pages 部署
dist/                 自动生成的完整 Markdown、HTML 与 PDF
```

章节 Markdown 是唯一正文源稿；不分别手工维护 Markdown、网页与 PDF 三份内容。`dist/` 为生成目录，后续默认不作为手工编辑的源文件提交，通过构建产物、发布版本和 Pages 提供下载。

| 交付物 | 约定与验收 |
| --- | --- |
| 分章 Markdown | 按目录组织，章节、图表、引用与附录可独立维护 |
| 完整 Markdown | 自动合并；标题层级、全书目录和内部链接正确；若含图，提供随附资源包 |
| 单页 HTML | 全文一页，目录导航、手机阅读、可访问的图文说明；内嵌必要样式和图像，下载后断网可读 |
| GitHub Pages | 部署同一 HTML 阅读版；实际部署成功、访问验证后再在 README 公布可用链接；Pages 站点同时提供成品下载 |
| 出版级 PDF | 独立分页排版：封面、扉页、目录、书签、页码、页眉、图题与注释，统一中文字体并检查嵌入，矢量图清晰、无表格溢出或不当断页 |

PDF 默认先制作适合阅读与一般打印的出版排版版；正式印厂所需开本、出血、色彩空间及 PDF/X 等规范在有具体出版需求时另行确定。构建工具在确认目录后选择，优先成熟工具与少量配置，避免引入需要维护的网页应用框架。

发布前检查内容与引用、各格式链接、断网 HTML、PDF 字体与代表页面。GitHub Pages 的实际部署与访问状态以 README 的阅读入口为准，不把拟定网址当成部署成功。
